# 泛用实体库：统一候选检索与原音复核

日期：2026-10-10。当前状态：已接入正式 Web 的“实体原音复核”，8051／8081 默认开启。下面保留离线原型与验证阶段的历史记录；接入结果见最后一节。

目标是在转录前预建领域词库，针对库内各类标准名使用同一套纠错机制。实体类型用于管理和展示，不参与候选阈值、提示长度例外或是否修改的判定。上一轮 `PERSON` 两字提示例外已撤回。

## 已经运行的统一流程

1. 先取得不含词库提示的 ASR 初稿。词库在音频开始前确定；本次没有用每条测试答案临时选词。
2. 在初稿中检索与标准名或登记别名字音接近的跨度。同一套拼音、字形、长度评分用于所有类型。检索只是召回候选，不直接替换。
3. 对候选所在的原音加少量候选标准名提示再次识别。本原型最多八个候选，复用现有 ASR 服务与提示复制保护，不修改 ASR 模型或 VAD。
4. 只将重识别支持的标准名复制回初稿的对应实体位置。左右最多八个归一化字符须一致；相邻已检索实体也可使用标准写法。重识别对其他句子、标点和普通词的改变不复制回来。
5. 多候选冲突、跨独立词边界、无法定位或重识别不支持时保留原文，留下候选、完整响应和修改日志。

这个流程适用于已有词库中的中文名称，名称是人名、地名、机构还是术语不会改变算法。当前召回覆盖 2–24 字中文标准名及登记中文别名；纯拉丁错读没有中文读音别名时尚未覆盖，完全丢失的实体也不能靠初稿相近字音检索。

## 实测结果

八个领域的 344 个音频/词库场景；其中 170 个触发重识别。候选选择只用初稿和预建词库，在真实样本中将所有实体类型改成 `ORG` 后结果完全相同。

|---|---:|---:|---:|---:|
| 法律 | 178/181 | 181/181 | 1.75% | 1.69% |
| 人名 | 10/18 | 18/18 | 7.08% | 4.72% |
| 医疗 FAQ | 75/79 | 77/79 | 1.44% | 1.30% |
| 金融、科技、科普、创业投资、农业 | 101/101 | 101/101 | 各域保持 | 各域保持 |

命中按标准名或已登记别名计数，例如‘汉斯’仍算 Hans 命中，不等于所有结果都已统一成标准名。合计命中 364/379→377/379，修改 11 个场景、恢复 13 次实体。344 个场景（338 个独立原音）中未观察到 CER 增加。另从相同公开语料中先按参考无该库词条筛出 56 个新的负例场景（48 个独立原音），15 个触发重识别，最终输出 56/56 与无提示初稿完全相同、未新增词库词。

首版锚点只允许原稿邻文，得到 9 个场景修复；相邻实体核对迭代复用相同真实 ASR 响应，得到上述 11 个场景修复。这个迭代是在已见开发材料上完成，不能把表格当作新的独立泛化评测。

## 接入正式流程的步骤

| 顺序 | 工作 | 验证内容 |
|---|---|---|
| 1 | 冻结当前统一规则，做新来源及说话人测试 | 更多未见名称、不同长度和混合文字；同时包含不含词库词的音频。同音但确为普通词的样本重点检查 |
| 2 | 在实体模块中封装候选与原音复核，只连接 Web 的实体会话状态 | 在真实精修流程中验证修正能够保留；失败、取消、断线、上下文不受支持时可靠恢复初稿 |
| 3 | 保留原音时间范围，只重放候选所在片段 | 当前后端没有词级时间戳，本原型重放整段短音频。长录音需在实体会话中记录音频块和分段事件范围，先验证截取不漏词，不修改 ASR/VAD 算法 |
| 4 | 上线为可选实体辅助模式，记录每次决定 | 展示候选、实际改动和复核状态；限制额外请求次数并测量用户等待时间 |

不直接把整个重识别文本覆盖初稿。最终实体来源需在进入精修前绑定已核实的标准词，并复核精修后的完整输出；本轮报告只比较原始 ASR 与局部实体修正，没有宣称正式 Web 的最终结果已改善。

## 限制与后续验证

带候选提示的第二次识别仍可能被词库诱导，并不是独立声学打分。完整同音词如果没有足够语境，单凭原音无法确定书写，应保留原稿或待确认。现有后端 token logprob 没有校准，不能将其直接当作纠错正确概率。

SpeechIO 的训练/留出划分按语句而非视频或说话人，可能有来源交叉；医疗 FAQ 属于已知词表覆盖测试。五个领域基线已满命中，能提供误改检查，不能证明这些领域的纠错收益。新负例仍来自相同语料，需要新的音频来源继续检验。部分音频出现在不同词库场景中；总计 400 个场景、386 个独立原音。

精修模型适合在“原写法/若干标准词/保留原文”的有限选项中提供语境支持；不能用自由改写结果替代音频证据。联网可用于转录前核对标准名、正式别名和来源，再冻结词库；不应把搜索结果是否热门作为转录中的替换依据。

复现入口：`experiments/scripts/evaluate_generic_entity_audio.py` 与 `evaluate_generic_entity_controls.py`。`plan.json`、各轮响应与输出已保存；原型没有写入正式实体数据库。

## 真实精修与长音频验证结果

403 个场景分别进入有相同实体库的现有 WebSocket/Refiner 流程：400 个短音频场景，另加 67.4、184.0、301.4 秒三个带完整参考的真人片段拼接压力样本。通用修改只在音频结束时重发修订的实体跨度及全部分段；前面的原始流式事件保持一致。最终修订不沿用旧 token logprob 作为新字形的置信度。实验没有改生产代码。

| 原型阶段／场景 | 基线最终命中 | 通用方案最终命中 | 最终 CER |
|---|---:|---:|---:|
| 法律 | 178/181 | 180/181 | 2.07%→2.02% |
| 人名 | 10/18 | 18/18 | 5.97%→3.62% |
| 医疗 FAQ | 75/79 | 77/79 | 1.52%→1.37% |
| 其他五域 | 101/101 | 101/101 | 各域保持 |
| 400 短音频场景合计 | 364/379 | 376/379 | 11 个场景改善，0 个场景退化 |

原始 ASR 阶段恢复 13 次，最终精修保留其中 12 次新增命中；两次相邻‘附加刑’被原有流程合并成一次。不改字形、只重发分段的控制组也合并原来的‘附加型’，所以这次丢失来自既有重复处理。没有改动非实体的重复、数字或精修算法。

实际执行 820 次 Web 会话与 345 次真实 Refiner 调用，包括 14 个只重发分段的控制会话。14/14 控制组最终文字与基线完全一致；389 个没有通用实体修改的场景在两组中的最终文字也完全一致。逐条非标点差异检查只见获原音复核支持的实体字形改动。生产 Python 与实验词库哈希验证通过。

| 长音频压力样本 | 基线/通用最终命中 | 基线/通用最终 CER | 额外 ASR 复核 |
|---|---:|---:|---:|
| 67.4 秒 | 4/11→9/11 | 7.85%→4.23% | 5.56 秒 |

CPU 检索在同一缓存响应上复测约 0.33–0.99 秒，跨度核对约 0.004–0.016 秒。长音频的额外 Web 精修耗时也增加，见报告；复核时的用户等待不止 ASR 调用本身。以上包含已见开发错例，不能用于宣称新的独立泛化准确率。

另外使用原有医疗视频播客 19:00–24:00 的真实连续五分钟原音，没有插入静音或重排片段。无提示 ASR 28.57 秒，候选检索 2.09 秒，额外原音复核 27.28 秒，跨度核对 0.06 秒。两处跨度改为‘黑色素瘤’。缺标准字幕，未把这些决定计为正确恢复，也未计算 CER；连续播客补测未运行额外精修。

## 正式接入与部署

正式算法位于 [entity_audio_repair.py](/home/aim0/桌面/tan/ASR/Codex-web/system/entity_audio_repair.py)。Web 的实体会话连接会缓存第一次识别原音，并在结束时调用此模块；不再由实验脚本预先写入修正文。仅修改实体模块、实体会话连接、实体页面开关及启动选项，ASR/VAD、数字与重复处理算法没有改动。

新页面选项“实体原音复核”在两个常驻 Web 服务默认开启。原“词库辅助识别”保留，二者互斥；已有实体保护、规范和精修继续运行。仅启用且为 `normalize` 的可检索中文标准名或中文别名参与新复核，所选领域继承原有通用条目。`preserve` 条目不被新模式修改。

29 项实体接入、失败回退与旧功能兼容测试通过。正式候选与跨度核对在 344 个冻结样本上与已验证原型完全一致。完整 403 场景通过正式 Web 接口重新运行，主识别与复核均检验相同 PCM，400 个短音频最终仍为 364/379→376/379、11 个场景改善、0 个场景退化。

五个场景又使用实际 ASR 服务和真实精修模型调用，四个正例分别复现‘防面过大→防卫过当’‘蒋涛→蒋韬’‘减伤分级→检伤分级’‘现保卡→健保卡’，一个不含词库姓名的负例不变。真实运行的 8051／8081 WebSocket 默认复核已确认，实际浏览器页面默认勾选与模式互斥已确认。没有导入实验词表至正式库，数据库哈希保持不变。

当前候选支持 2–24 字中文形及登记中文别名；短音频无可定位上下文、候选或原音不支持时保留原稿。初稿超 6,000 字或音频缓存超约两小时会跳过复核。长音频全量重放开销及新来源/说话人和同音普通词歧义验证仍是后续优化事项，这些限制不再作为阻止当前已验证功能接入的理由。
