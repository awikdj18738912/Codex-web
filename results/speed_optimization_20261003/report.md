# 2026-10-03 转录速度优化复测

结论：本轮没有保留新的运行优化。CPU 线程限制和 TF32 试验均已关闭，保留上一轮已验收的 WebSocket 关闭压缩设置。未修改 ASR、Refiner、数字规则、门控、提示词、校验器或前端显示逻辑。

## 完整音频对照

音频 4 时长 724.437 秒，音频 5 时长 843.256 秒。使用项目原有离线流式处理路径：16 kHz 单声道 Float32 PCM、1 秒传输块、2 秒文件解码间隔、Silero VAD、固定 K=3 窗口、v90 数字规则库开启、最终全文精修关闭。计时从建立 WebSocket 连接到收到最终结果，文件解码和启动暖机不计入。

基线执行两轮，顺序为原配置第一轮 → CPU 单线程两轮 → 恢复原配置第二轮 → TF32 一轮。TF32 在完整音频测试中未出现收益，因此没有继续第二轮。

| 音频 | 原配置两轮均值 | CPU 单线程两轮均值 | TF32 一轮 |
| --- | ---: | ---: | ---: |
| 音频 4 | 54.385 秒 | 54.336 秒 | 54.395 秒 |
| 音频 5 | 81.403 秒 | 81.358 秒 | 81.515 秒 |

CPU 单线程的差异不足 0.1%，不能认定为稳定提速。TF32 的整段耗时没有改善。TF32 中音频 5 的 Refiner 调用累计耗时约 40.30 秒，而原配置约 42.6 秒；这一局部改善没有转化为整段收益，不能把精修调用耗时与 ASR 耗时直接相加，因为它们存在并行重叠。

## 内容验收

以上各轮音频 4、5 的原始转写和最终精修文本均与原配置第一轮逐字一致，包括数字写法、标点及重复词处理。精修调用次数始终为音频 4 的 16 次、音频 5 的 158 次。

每轮保存完整文本和指标，源码及规则库二进制哈希也保存于各 JSON 的 `_speed_benchmark.configuration.hashes`。Refiner、Web、前端以及规则库二进制的哈希在全部试验期间保持不变；测试差异只通过 Web 进程环境变量启用。

## 撤回范围与服务状态

- CPU 单线程试验使用 `OMP_NUM_THREADS=1`、`MKL_NUM_THREADS=1`，恢复时均移除。
- TF32 试验使用 `TORCH_ALLOW_TF32_CUBLAS_OVERRIDE=1`，恢复时移除；没有把这一降低内部计算精度的设置加入默认启动脚本。
- 最终 Web 重新启动时不含上述试验环境变量，Qwen ASR 始终复用原进程，未重启。
- 恢复后再次完整转录音频 4、5，耗时分别为 54.685 秒、82.409 秒；两段原始转写与精修文本均逐字匹配基线，失败调用为 0，连接仍未协商 WebSocket 压缩。恢复后也有小幅计时波动，因此不以单次差异认定优化收益。
- v90 数字规则库、原有浮点计算精度、精修阈值、模型权重和提示词均保留。
- 原有 Web 测试 51 项、Refiner 测试 1 项通过；报告脚本语法和 diff 检查通过。

没有删除用户原有修改，也没有新增针对某个词语的精修规则。新增的 `scripts/report_speed_followup.py` 仅用于整理试验结果，不参与转录服务运行。
